# Inventario inicial de formularios de A&O ERP

**Fecha:** 3 de noviembre de 2026  
**Base:** 27 módulos de gestión parroquial y Dashboard descritos en la directriz institucional.  
**Propósito:** clasificar lo presente en las pantallas; no acredita que un módulo esté funcionalmente terminado.

## Criterios de lectura

- **Parcial**: existe una superficie de captura o preferencias, pero no satisface todavía todo el estándar (validación asociada, estados, acciones, comportamiento accesible y/o responsividad verificados). En el prototipo muchas acciones son vistas previas sin persistencia.
- **No aplica**: la pantalla revisada es principalmente de consulta y solo contiene filtros, búsqueda, conversación o selección; no se encontró un formulario de edición/alta independiente.
- **Pendiente**: el módulo necesitaría captura por su finalidad, pero no se encontró una pantalla de formulario en el código revisado. La modalidad indicada es recomendación para una fase posterior, no funcionalidad existente.
- La modalidad recomendada puede diferir de la superficie actual. “DetalleDrawer” es una ficha de consulta salvo que se indique que se utiliza para captura.

## 3. Lectura del inventario

- Se encontraron 11 pantallas que importan `FormDialog`: comunidad; comunicaciones; liturgia; agenda; administración institucional; compras; estructura eclesiástica; documentos/certificados; gestión sacramental; libros sacramentales (consulta avanzada); usuarios/permisos.
- `DetailDrawer` se reutiliza en múltiples pantallas principalmente para consultar detalles; no es un componente de formulario lateral terminado.
- Las pantallas emplean controles UI instalados (`Input`, `Select`, `Textarea`, `Calendar` y otros). `FieldGroup` entrega una etiqueta visual básica, pero no gestiona obligatoriedad, error ni estado de validación.
- Existe `src/components/ui/form.tsx` con integración a React Hook Form y mensajes asociados, pero no se encontró su uso desde las pantallas de los módulos revisados.
- No se encontraron componentes dedicados `FormPage`, `FormDrawer`, `FormSection` o `FormActions`.
- La clasificación refleja la implementación encontrada, no operaciones productivas ni permisos reales.

## 4. Orden sugerido de migración

1. Resolver la diferencia de paleta/tipografía señalada en `docs/erp/estandar-formularios.md` antes de fijar miniaturas o tokens distintos.
2. Definir y validar la estructura de campos, errores, acciones y accesibilidad usando las primitivas existentes, sin añadir dependencias.
3. Migrar un modal breve de bajo riesgo (por ejemplo, agregar responsable) como caso de validación del patrón estándar.
4. Revisar un panel lateral de edición y una página ampliada antes de extender el patrón a módulos sensibles.
5. Migrar por módulos y actualizar esta tabla después de cada fase aprobada.
6. Considerar Intenciones de Misa como caso posterior únicamente con autorización independiente; el inventario actual no añade ese formulario.
