1. RESUMEN EJECUTIVO
================================================================================
La auditoría técnica del repositorio D:\Proyectos\ao-erp confirma que las tres aplicaciones (apps/erp, apps/saas y apps/diocesano) operan actualmente como aplicaciones frontend con persistencia demostrativa local en window.localStorage y datos en memoria. No existe todavía conexión activa a PostgreSQL, Supabase Auth, Supabase Storage, Realtime, Edge Functions ni migraciones SQL ejecutables.

Al mismo tiempo, el ecosistema cuenta con un diseño lógico y relacional avanzado (Documentos 01 a 15 en docs/arquitectura/backend/ y los informes de cierre de Nivel 1), una frontera inicial de server functions en apps/erp (src/start.ts, src/server.ts, CSRF middleware) y pruebas técnicas recientes en apps/saas (src/server-functions/vercel-runtime.ts, src/server-functions/module-access.ts).

Esta auditoría concluye que Supabase administrado (PostgreSQL + Auth + Storage privado) es viable como plataforma inicial para acelerar la salida a producción, siempre que se adopte una arquitectura desacoplada del proveedor (Decisión D-14) que garantice:
1. PostgreSQL estándar como único motor de verdad, sin lógica de negocio cautiva en Edge Functions ni consultas directas desde componentes React.
2. Identificador interno propio de usuario desacoplado del proveedor de identidad (auth.users) y validación doble (servicios server-side propios + PostgreSQL RLS).
3. Interfaz abstracta de almacenamiento (DocumentStoragePort) compatible con Supabase Storage, AWS S3 y MinIO autohospedado, con metadatos en PostgreSQL y sin binarios en la base de datos.
4. Separación estricta de ambientes (Desarrollo, Pruebas/Staging y Producción) y verificación previa de compatibilidad del runtime de despliegue (hoy el preset @lovable.dev/vite-tanstack-config compila por defecto para cloudflare-module).

Dictamen para Nivel 2.2: APTO CON OBSERVACIONES (requiere aprobación expresa del propietario sobre D-14, las decisiones bloqueantes de Fase 1 del Nivel 1 —D-03, D-12, D-13— y los parámetros de proveedor/región/runtime antes de escribir DDL o conectar servicios).

4.1 ¿Existe un proyecto Supabase adecuado o conviene crear uno nuevo?
- Estado verificado: no existe ningún proyecto Supabase conectado, configurado ni referenciado en el repositorio.

4.2 Evaluación por capacidad
- PostgreSQL administrado: RECOMENDADO inicialmente. Motor estándar con pgcrypto, FKs compuestas, triggers contables y RLS. Bajo acoplamiento si se usa SQL estándar y servicios server-side de A&O (evitando PostgREST directo desde la UI).
- Supabase Auth: RECOMENDADO como proveedor inicial (PKCE, recuperación, verificación, MFA). Requiere tabla interna core.users / core.user_identities y AuthProviderPort para no depender de auth.users ni de user_metadata editable.
- Supabase Storage: RECOMENDADO como opción inicial para binarios privados detrás de DocumentStoragePort, sin exponer storage_key ni buckets públicos.
- Supabase Realtime: NO requerido en Fase 1; opcional a futuro solo para avisos no sensibles.
- Supabase Edge Functions (Deno): NO recomendadas para reglas de negocio por alto acoplamiento de runtime; toda lógica de negocio debe residir en los servicios server-side propios de A&O.

================================================================================
Flujo desacoplado:
Navegador (React 19 + TanStack Router)
  -> createServerFn + CSRF + Cookie HttpOnly
  -> Frontera Server-Side A&O (TanStack Start / Node)
  -> Middleware Auth + RequestContext (org, entity, campus, entitlements)
  -> Servicios de Dominio Propios (core, saas, erp, pastoral, sacramental, diocesan)

     * AuthProviderPort -> [Inicial: Supabase Auth | Futuro: Keycloak/BetterAuth/OIDC]
     * Repositorio / SQL Pool -> [PostgreSQL 16/17 estándar + RLS: Supabase / Neon / DO / Autohospedado]

- packages/domain (futuro): contratos TypeScript, DTOs y esquemas Zod compartidos, sin dependencias de Supabase ni acceso a BD.

6. ESTRATEGIA DE PORTABILIDAD DE BASE DE DATOS
================================================================================
- Motor único estándar: PostgreSQL 15/16/17 compatible con Supabase, Neon, DigitalOcean, AWS RDS o autohospedado.
- Extensiones mínimas: únicamente pgcrypto (prohibido depender de extensiones propietarias de un único proveedor para lógica de negocio).
- Esquemas lógicos: core, saas, erp, pastoral, sacramental, diocesan, audit y esquema interno no expuesto app_internal.
- Funciones, triggers e índices portables: PL/pgSQL estándar (trigger partida doble SUM(debit)=SUM(credit), inmutabilidad de comprobantes posted/reversed), FKs compuestas (organization_id, id), índices parciales estándar y bloqueos SELECT ... FOR UPDATE.
- Migraciones SQL versionadas en Git: secuencia ordenada M0..M12 ejecutables con psql estándar o Supabase CLI solo como runner de SQL puro.
- Exportación/Importación y pruebas de restauración: pg_dump --format=custom --no-owner --no-acl por esquemas de aplicación (excluyendo esquemas auth/storage del proveedor) + restauración obligatoria con pg_restore en una instancia PostgreSQL independiente (Docker/servidor secundario) verificando integridad contable y pruebas negativas RLS.
- Migración con interrupción mínima: aprovisionamiento de destino con migraciones Git -> replicación lógica nativa PostgreSQL (CREATE PUBLICATION / CREATE SUBSCRIPTION) o ventana breve controlada -> sincronización de objetos Storage verificando checksum_sha256 -> conmutación de DATABASE_URL / AUTH_PROVIDER / STORAGE_PROVIDER -> smoke tests.

7. SEGURIDAD Y AUTENTICACIÓN
================================================================================
7.1 Identificador interno independiente del proveedor
- Brecha resuelta respecto a Doc 15 §4.1: evitar que core.profiles, core.memberships y auditoría tengan FK física directa a auth.users(id) de Supabase.
- Diseño portable:
  * core.users (id uuid PK, primary_email, status, mfa_enforced, timestamps).
  * core.user_identities (id uuid PK, user_id FK -> core.users(id), provider, provider_subject, UNIQUE(provider, provider_subject)).
  * Todas las tablas de negocio referencian a core.users(id). Al autenticar con Supabase Auth inicialmente, el servicio mapea el sub del JWT a core.users.id.

7.2 Sesiones, RBAC, RLS portable, aislamiento pastoral y auditoría
- Sesiones SSR: cookies HttpOnly, Secure, SameSite=Lax, Cache-Control: no-store, PKCE y protección CSRF (createCsrfMiddleware en src/start.ts).
- Autorización doble: validación en servidor (membresía activa, scope, rol, entitlement) + PostgreSQL RLS en todas las tablas expuestas.
- RLS portable: función app_internal.current_user_id() que resuelve SET LOCAL app.current_user_id (conexión directa server-side en cualquier PostgreSQL) y, cuando aplique JWT Supabase, mapea auth.uid() vía core.user_identities.
- Separación plataforma vs. institución: is_platform_role = true opera solo en core/saas/audit plataforma y tiene bloqueado erp, pastoral y sacramental.
- Aislamiento pastoral: pastoral.pastoral_care_cases + pastoral_care_confidential_notes en tabla separada con ACL relacional (case_role_acl, case_member_acl) y emergency_grants de máximo 4 horas auditados.
- Auditoría: tablas append-only en audit.* con REVOKE UPDATE, DELETE.

8. ALMACENAMIENTO DOCUMENTAL
================================================================================
- Interfaz desacoplada DocumentStoragePort (adaptadores: SupabaseStorageAdapter inicial, S3CompatibleStorageAdapter para AWS S3 / R2 / MinIO propio).
- Prohibido almacenar binarios en PostgreSQL (salvo justificación técnica documentada excepcional). PostgreSQL conserva únicamente metadatos en erp.document_file_metadata + tablas puente tipadas (D-11).
- Buckets privados: storage_key nunca se entrega al cliente; descargas mediante autorización server-side y URLs firmadas de corta duración, registrando cada acceso en audit.sensitive_access_events.
- Validación de MIME real (firma binaria), límite de tamaño, checksum_sha256 y estado malware_status (pending_scan -> clean | rejected | quarantined).
- Retención, legal_hold y eliminación lógica controlada (sin borrado físico mientras existan referencias históricas o retención vigente).
- Copias de seguridad independientes: versionado de bucket y replicación/sincronización cifrada del almacenamiento de objetos independiente de pg_dump, validada por checksum_sha256.

11. DECISIÓN ARQUITECTÓNICA PROPUESTA: D-14
================================================================================
D-14 — Independencia del proveedor y portabilidad de infraestructura:
- A&O ERP, A&O SaaS y A&O Diocesano utilizarán PostgreSQL estándar como motor único de persistencia y una arquitectura desacoplada del proveedor.
- Supabase podrá usarse como infraestructura inicial, manteniendo bajo control exclusivo de A&O: reglas de negocio en servicios server-side propios, identificador interno core.users, migraciones SQL estándar versionadas en Git y puerto DocumentStoragePort compatible con Supabase Storage, S3 y MinIO.
- La arquitectura debe permitir sustituir progresivamente proveedor de PostgreSQL, autenticación, almacenamiento y servicios auxiliares (Paperless-NGX) sin reconstruir módulos.
- Estado: REQUIERE APROBACIÓN EXPRESA DEL PROPIETARIO.
